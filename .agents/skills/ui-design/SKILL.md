# LLM Wiki UI design

새 화면이나 큰 UI 개편을 할 때 이 지침을 기본 시각 기준으로 사용한다. 제품은 사용자가 생각을 말하면 작업이 Capture → Problem → Solution으로 정리되는 로컬 지식 작업 공간이다. 화면은 작업의 맥락을 보존하고 현재 결정에 필요한 것만 앞에 두어야 한다. 작업자를 점수화하거나 생산성 순위처럼 보이게 하는 표현은 피한다.

## 시각 방향

- 현재 토큰을 먼저 재사용한다: 크림색 `--color-bg-primary`, 흰 표면, 짙은 잉크 텍스트, 낮은 대비의 경계와 그림자, 절제된 핑크 `--color-accent-primary`, 민트·레몬 상태색. 새 색은 의미가 분명할 때만 토큰으로 추가한다.
- `--font-family-body`의 Nunito/Noto Sans KR로 읽기 흐름을 만들고, `--font-family-mono`는 상태, 경로, 메타데이터처럼 기계적인 정보에만 쓴다. 제목은 짧고 강하게, 본문은 편하게 읽히게 한다.
- `--space-*`, `--radius-*`, `--shadow-*`를 중심으로 리듬을 만든다. 넓은 여백으로 주요 영역을 묶고, 카드·패널·대화상자의 깊이를 경계와 약한 그림자로 구분한다. 둥근 모서리, 장식, 그라디언트는 계층을 돕는 범위에서만 사용한다. 기존 값이 지나치게 작거나 흐리면 그대로 복제하지 말고 읽기 크기·대비·포커스 가시성을 우선해 조정한다.
- 한 화면에 하나의 분명한 주 작업과 하나의 시각적 초점을 둔다. 보조 정보는 접거나 낮은 대비로 두되 발견 가능해야 한다. Capture는 작게 유지하고, 진행 중인 Solution과 현재 결정을 명확히 드러낸다.
- 화면을 먼저 큰 덩어리로 구성한다: 내비게이션, 현재 작업 영역, 보조 맥락 영역의 폭과 정렬을 정한 뒤 제목·메타데이터·주요 행동·세부 내용을 배치한다. 넓은 빈 공간, 비대칭 정렬, 작은 색 포인트처럼 제품의 따뜻한 성격을 드러내는 한두 가지 특징을 의도적으로 선택하되 장식이 작업보다 앞서지 않게 한다.
- 모션은 상태 변화와 공간 관계를 설명할 때만 짧고 부드럽게 사용한다. 기존 `--motion-fast`와 `--motion-normal`을 우선하고, `prefers-reduced-motion`에서는 전환·자동 재생을 줄인다.

## 구현 기준

작업 시작 시 저장소 루트 기준 `frontend/src/theme/tokens.css`, `frontend/src/components/`, 변경할 `frontend/src/features/` 화면과 `docs/product-spirit.ko.md`를 필요한 범위만 읽는다. `frontend/src/theme/legacy-components.css`와 스타일이 충돌하는지도 확인한다. 구현 전에 주 작업, 정보 계층, 이번 화면의 시각적 특징을 짧게 정하고 이를 기준으로 결과를 검토한다. 기존 화면의 약점까지 복제할 필요는 없다. 반복되는 개선은 공유 토큰이나 컴포넌트에 반영하되 영향받는 화면도 확인한다.

먼저 기존 화면, 컴포넌트, 토큰을 확인하고 동일한 패턴을 재사용한다. 새 UI에는 기본·hover·focus-visible·pressed·disabled 상태와 로딩·빈 상태·오류·성공 상태를 함께 설계한다. 키보드 순서, 명확한 포커스 링, 충분한 대비, 의미 있는 버튼 이름과 ARIA 레이블을 보장한다. 클릭 영역은 데스크톱에서도 여유 있게 두고, 정보가 많아져도 작업 흐름이 무너지지 않도록 좁은 창과 넓은 창을 모두 점검한다.

한국어와 영어 전환을 고려해 문자열을 하드코딩하지 말고, 번역 길이 증가와 줄바꿈을 수용한다. 사용자에게 보이는 한국어에서는 사람을 `사용자`로 표현한다. 저장되지 않은 입력, 현재 view, workflow lineage를 불필요하게 잃지 않도록 기존 제품 원칙을 따른다.

## 검토와 전달

실행·캡처 환경이 제공되면 실제 앱의 대표 화면을 넓은 창·좁은 창·키보드 상호작용으로 확인하고, 렌더링 또는 스크린샷을 직접 보고 검토한다. 한국어·영어와 긴 실제 수준의 콘텐츠를 사용한다. 다음 항목에 문제가 있으면 수정 후 해당 화면을 다시 확인한다.

- 첫눈에 주 작업과 현재 상태가 구분되는가? 모든 요소가 같은 크기의 카드나 같은 강도의 버튼으로 경쟁하지 않는가?
- 정렬, 간격, 표면의 깊이가 일관되고 본문이 편안하게 읽히는가? 작은 글씨와 흐린 색으로 정보를 과도하게 숨기지 않았는가?
- 긴 제목, 빈 데이터, 오류에서 겹침·잘림·가로 넘침이 없는가? 화면을 줄여도 주요 행동에 접근할 수 있는가?
- 포커스가 보이고 키보드로 주요 작업을 수행할 수 있는가? 색만으로 상태를 전달하지 않는가?

실행 환경이나 캡처 도구가 없으면 그 한계를 숨기지 말고 코드 기반 검토 범위를 명시하며 시각 검증을 완료했다고 보고하지 않는다. 작업 범위에 맞는 테스트와 `git diff --check`를 실행한다. 최종 전달에는 디자인 결정과 확인한 화면·상태, 남은 제한을 짧게 설명한다.
