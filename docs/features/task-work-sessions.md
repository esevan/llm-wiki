# Task work sessions

Delegated Codex output stays isolated from its parent Run. Approvals that cannot be tied to an active Run are rejected instead of being shown under the parent.

[한국어](task-work-sessions.ko.md) | **English**

The Sessions tab in Task detail keeps focused work separate from the Task's canonical definition and Work Log. Its left rail lists saved sessions while the conversation remains the main workspace. Opening a Task does not load session history or start Codex session services; that work starts only after you select **Sessions**. A Task starts with no sessions. Choose **New session** when you want one, or choose **Link Codex session** to attach a saved conversation from Codex CLI, the Codex app server, or the VS Code extension in the same local Codex home. Linking can create the Task session in one step and does not start or resume provider work.

Each session stores chat-style user notes, one optional file up to 10 MB per note, and its own title and execution settings. Pasted images show a preview before saving; saved images remain visible and every saved attachment can be downloaded. A failed save leaves the note and attachment in the composer for retry. Saved records survive an app restart; unsaved drafts are retained while Task detail remains open, but are not restored after restart.

The conversation shows user messages, all Codex prose as Markdown, and tool activity in provider order. Repeated final prose is shown once. Commands appear as compact rows whose bounded, preformatted output opens on demand, while a visible status marks queued, running, or response-needed work. Task context and execution settings remain available in collapsible sections below the conversation. The context reads the current Task and references without saving a second snapshot, and another Task's sessions are never included.

Only a persisted, inactive Codex conversation that is not owned by another Task can be linked. A local target that already contains notes or Runs cannot absorb an unrelated history. This prevents two records from being silently combined.

Provider, model, approval reviewer, and project folder path are saved with each session. **Prepare conversation** connects the exact session to Codex and checks its effective settings without starting work or creating a Run. Afterward, **Check settings** refreshes that result. **Save note** records only the note and attachment. **Run with Codex** is a separate explicit action: it saves one immutable Run and linked Work Log row before Codex starts. The session retains one exact Codex conversation across later Runs, without replaying the previous transcript.

The project folder can be entered directly, selected from the native **Browse** picker, or chosen from the ten most recently saved session folders. Browse only returns a path; it does not change the Vault. The folder is still validated by Codex preparation and execution before work starts. Execution instructions keep file discovery within that project folder and require explicit approval before searching broader external paths; this is an instruction boundary, not an operating-system sandbox.

Runs appear in the conversation at their actual time alongside linked Codex history. The current Run keeps its status, Stop action, approvals, and questions visible even when an older Run is selected. Live assistant text appears in the conversation; command output and implementation evidence remain expandable so they do not displace the composer. High-volume updates are processed in provider order, so an output burst does not replace the retained result with an event-delivery error. The Work Log synchronization state stays visible independently of the provider outcome. Stop only requests interruption; the provider's final status determines whether the Run finished, failed, or was cancelled. Failed, cancelled, interrupted, and uncertain Runs keep their evidence and provide **Retry Run** beside the saved attempt. Retry starts a distinct Run with the previous instruction and a link to the original Run; it does not send the current composer draft or attachment. An interrupted or uncertain result can include work that already happened, so review its saved evidence before retrying. Retry is available only after execution settings are prepared and while no other Run is active. If a retry response is lost, repeating the action uses the same operation identity to avoid creating an accidental duplicate. **Use instruction again** remains a separate action that loads a prior instruction only when the composer is empty and never overwrites another draft.

The composer remains available while a Run is active. Press **Enter** to use the primary **Run with Codex** action, or press **Shift+Enter** to add a line break. Enter used to confirm Korean or another IME composition does not send. **Save note** records local context without invoking Codex. A draft attachment shows whether it is ready or being sent with the current Run. After a Run submission succeeds, its preview clears; a failed submission keeps the attachment available for retry. Images attached to a Run are forwarded to Codex; attachments saved as notes remain part of the session record and can be downloaded later.

Formal approvals expose only the choices sent by Codex. Structured questions require one explicit submission after each non-secret answer is chosen or entered; stale requests are disabled and failed answers remain available to retry. A Work Log execution block links back to its exact session and Run. Codex execution never completes a Task, resolves a Problem, or publishes Knowledge. See the [feature specification](../../specs/014-task-codex-execution/spec.md) for the complete boundary.

After a Run reaches a terminal state, its Work Log can show a readable **Execution summary**. The saved final report is primary; completed command, file, and check evidence appears only when it materially corroborates, adds to, or contradicts that report. Each claim identifies whether it was suggested, decided, attempted, performed, observed, or verified and exposes its exact saved sources. A missing final report produces a factual fallback without inventing a decision or successful outcome. The original Run remains available from the Distillation. Original execution evidence is collapsed by default. An ordinary command exit is an observation, not proof that the implementation is correct; stronger labels require canonical evidence. Retry and repair target that exact saved Run, including older Runs.

The same validated result updates **Current decisions and evidence** in the Task journey without another model pass. Explicit saved decisions can become current, superseded, withdrawn, or unresolved topic states; ordinary AI prose cannot count as adoption. Prepared node detail opens from local saved data and keeps the original recorded event trace separate. If a source changes, the last good view stays visible with a stale label while a durable refresh runs. Transient failures retry automatically within the bounded job policy, and an exhausted job can be retried without rerunning the originating Codex Run.

**Ask me** keeps approvals with the user; **Automatic review** requires an explicit current choice and preserves Codex’s configured approval policy and sandbox. Legacy automatic preferences do not grant approval.

Using a session does not complete or reopen a Task. Saving a note does not invoke AI.

The external session list and linked history are paginated snapshots from the same local Codex home. By default LLM Wiki leaves Codex's normal local home in use (`~/.codex`), so conversations saved by Codex and the VS Code extension are visible to the linker. In **AI setup**, choose **Use a different Codex home for LLM Wiki** only when an intentionally isolated store is needed; the folder must already exist and restarting LLM Wiki applies the choice. Use **Load more** to retrieve additional conversations or older turns. LLM Wiki refreshes the exact bound conversation when its session opens, but changes made simultaneously by another Codex process are not guaranteed to stream into the view. Continuing that conversation still requires an explicit **Run with Codex** action.

The execution summary covers only its Run, normally in 2–3 concise statements grounded in the saved final report and relevant completed evidence. Important failures, blockers and unfinished work remain visible beyond this default length. Reported assertions and drafts never establish delivery, real-world completion or independent verification. Legacy empty projections and generation failures offer original-record access and explicit retry; missing reports, pending summaries and execution failure remain distinct. Truncated raw text is never substituted for a summary.

The Work Log presents **Requested → What Codex did → Result**. Requested is the immutable instruction saved on that exact Run, including later turns in the same session; older entries without it say the original request is unavailable and never substitute the current Task description. The basic view shows up to three saved summary claims plus all unresolved or contradicted claims, failures and limitations. Report-only assertions are phrased as Codex reports, and drafts retain their saved wording. Summary details, claim states and exact sources are collapsed, as are original execution records; expanding them preserves traceability and access to the exact session and Run. No historical data is rewritten.

## Hold and execution backlog

Workbench cards and titles open Task detail whenever a canonical Task exists; Captures and legacy Problem items open their appropriate refinement. Explicit **Refine** remains available. Background clicks exclude nested controls, links, child cards, disclosures and text selection.

The **⋯** menu replaces the old Delete button. In-progress Tasks offer **Put on hold / Move to execution backlog / Delete**; held Tasks offer **Resume / Move to execution backlog / Delete**. Other states, Captures and legacy Problems offer Delete only. Delete remains a separated last item using the existing confirmation. Keyboard users can open the menu, navigate with arrows/Home/End, and dismiss with Escape to return focus.

**Put on hold** moves work into one shared, collapsed **On hold (n)** area near active Tasks without undoing refinement. **Resume** returns the same Task and sessions to active work. **Move to execution backlog** places it in Refined Tasks without asserting readiness. An explicit backlog placement takes precedence over an open refinement session, which remains intact. Returned Subtasks appear directly in this lane while retaining their parent link. Starting again clears this placement override.

All actions preserve content, refinement revisions, work records, sessions and the first start timestamp. New transitions have dedicated history visible under **State history** in detail. Completed Tasks still require the existing explicit reopen action.

The server rejects hold/backlog moves while any session of the Task has a queued, running or awaiting-response execution, or an uncertain dispatched execution needing attention. Finish the execution or explicitly stop it and confirm its end before retrying. This menu currently has no action to reconcile an uncertain execution or override that guard. Holding a Task never silently cancels an agent. Starting a new execution while held is also rejected; resume the Task first.

The collapsed hold area is a compact title/count row, including when empty. Expanding it shows one horizontal row of fixed-width cards, with horizontal scrolling and keyboard focus; it does not wrap into vertical lanes or extend behind the category board.

## Completed Tasks and new notes

Completion freezes the Task definition, checklist, prior Work Log evidence and saved execution history. Existing session settings cannot be edited and new Codex Runs cannot start on a completed Task. Late provider results, image summaries and Work Log distillations cannot overwrite completed evidence. Finish or stop an active or uncertain execution and confirm its end before completing its Task; the same rule applies when the final Subtask would complete its parent. Terminal status and the saved final report commit together.

New user notes remain available through **Save note**, including attachments. On completed Tasks, Enter saves a note and never starts Codex. They append to the existing session-entry path without replacing previous entries, changing Task state or rewriting Work Logs. A new session can hold notes when no session exists. Notes dated at or after completion are labeled **Post-completion note**. The saved execution history remains readable, and the separate Knowledge editing, review and publication flow remains available.

## Execution environment and follow-up requests

Session labels come from the first saved user request/note, falling back to the existing conversation label. Labels are not manually edited; historical stored titles are preserved. The conversation uses one session rail; Task context, history and execution environment are disclosures. Completed Tasks disclose optional post-completion notes and offer no Run action.

Execution environment keeps project folder, model and approval reviewer as reusable session settings. **Reasoning effort** offers **Inherit default · Codex settings** plus only the selected model's reported levels. **Refresh supported models** reads local Codex's model capabilities. Unsupported effort after a model change resets to inheritance with a visible warning; save and prepare again. If capabilities/configuration cannot be confirmed, inheritance is still available for the existing manual path, but new follow-up requests require a resolved reasoning setting. Model and reasoning settings do not alter AI setup's separate endpoint/model routing. A bound conversation's folder is read-only; use a new session for another folder. Existing active or completed Runs do not permit session settings edits. Save changed settings before preparation; preparation does not start work.

While a Run is active, the same composer accepts additional work through **Add to pending requests** (including Enter; Shift+Enter and IME composition retain their prior behavior). This enqueues a follow-up and does not steer the active Run. **Save note** stays separate. Each pending request shows its order, project, model and resolved reasoning; pending requests support revision-checked edit, remove and up/down ordering. Settings are captured when enqueued, including the consent/settings revision. Later defaults never silently update pending requests. A settings or consent change pauses the queue; remove and explicitly requeue the affected request after reviewing and preparing the intended environment.

Pending requests run sequentially through the existing execution service after confirmed successful completion. They do not create a Work Log entry until actually dispatched. Each dispatched request retains its own immutable Run, request, final report and Work Log source links. Serialization is per session; separate sessions are not a project-wide lock.

**Stop current work, then run pending requests** requests interruption of the exact active Run and waits for its confirmed provider termination before starting the pending list. Acknowledgement of Stop alone is insufficient. **Cancel pending execution** cancels the drain intent and pauses the list; it cannot retract an already delivered interrupt or undo work. Ordinary **Stop** pauses automatic follow-ups. Approval/input waits retain the active Run, while failure, cancellation or uncertain outcomes pause follow-ups for review. No uncertain request is automatically resent. Explicit resume starts pending instructions, not a retry of the failed Run.

Pending requests are stored natively and survive closing Task detail. The active request's unsaved composer, answers, attachment and queue editor are retained through the existing in-memory Task/session draft store; do not rely on them surviving app restart. Upgrading an existing session requires one fresh preparation before execution settings are considered ready. Restart places automatic queues in a review-required state and preserves uncertain provider outcomes. Pending work must be cancelled before completing or holding the Task. Completed Tasks cannot enqueue, edit settings or dispatch; append-only notes and the separate Knowledge flow remain available. Queue actions never mark a Task complete or publish Knowledge.

Repeated preparation refreshes model/reasoning metadata against the same verified live conversation; it does not resume that conversation from disk merely to refresh settings. After a provider restart, a missing conversation remains an explicit error. The existing session and history are preserved; retry the original Codex connection or explicitly create a separate session.

Unprepared sessions open execution setup before conversation history. New/link actions belong to session navigation, and running work uses an additional-request composer. Current approval/input appears before history. Cancelling unsaved environment changes restores saved settings while keeping the request draft. Completed history omits session creation/linking and retains its separate note disclosure.
