# Compatibility audit — current working behavior must remain

Design review only at baseline `7a3c7f7`; Compass integration `9940d91` inspected with git show. No production implementation, reproduction experiment or baseline suite rerun in this design task. Items below are **regression risks of the proposed change**, not claims that current working features are broken. Existing tests listed are source-inspected coverage, not newly executed passes.

## Recommended implementation boundary

Keep existing TaskExecutionService and native TaskExecutionRuntime authoritative. Wrap/reuse prepare, execute, subscribe, interrupt, formal respond, exact thread link/read and Work Log sync. Add a separately persisted queue scheduler calling these same paths; do not replace them with chat-component state, a second event router, a second provider client or new log serialization. Land visual reorganization first with queue off, additive reasoning contracts second, then queue backend behind unchanged manual execution pathways. Preserve old saved records and unknown model values. No schema/destructive data migration just to rename display labels.

## Persisted queue design and scope

New tables/contracts, not a reuse of Run status `queued`: queue controller keyed by Task+session with revision, mode active/paused/stop_then_drain/reconcile_needed and exact stop target Run/provider thread/turn/generation. Item states `pending_validation`, `pending`, `claimed`, `linked_run`, `cancelled`, `blocked`; terminal outcome is stored on linked immutable Run. Stable item ID + edit revision + enqueue operation ID + claim token + linked Run ID + immutable instruction/attachment digest + resolved execution settings snapshot are required. Maintain numeric sortable order with revision-checked reorder; only unclaimed items editable.

One SQLite immediate transaction must recheck ownership/Task mutability/hold/uncertain dispatch/current session active Run, atomically claim the head and create/link the existing Run+Work Log records. Calling current create_run in a separate transaction after claim is insufficient without a recoverable outbox/claim protocol; extend transaction-scoped service internals rather than duplicate writes. Exactly one locally claimed active execution per session is the goal, not exactly-once external side effects.

Persist enqueue and stop-and-drain intent before acknowledging UI success. Provider call occurs after transaction. Crash after provider may have accepted but before response is inherently uncertain; mark reconcile_needed and stop. An operation ID deduplicates local records and normal retries; it is **not evidence of provider-side exactly-once execution**. Existing recovery correctly keeps uncertainty; preserve that behavior.

Session settings are snapshot at enqueue after preparation: requested mode (explicit/inherit), resolved model/effort/canonical cwd/reviewer/policy/sandbox/settings revision, capability revision and provenance. Inherit must be resolved before dispatch eligibility. Unknown effective reasoning → pending_validation, not fabricated cache default. Native validation/permissions remain current at dispatch; revoked access, model loss, folder rebinding or changed security consent pauses for explicit revalidation. Changing defaults never mutates existing queue items; reapply is explicit, revisioned and visible.

Normal confirmed success advances; formal wait keeps current Run; failure/cancel/uncertainty pauses. Explicit stop-and-drain permits advancement only after exact target's confirmed terminal result and one-time intent consumption, with terminal success race handled too. Stop alone pauses queue. Cancelling drain cancels future auto-start, cannot undo delivered interrupt or side effects. Modal close leaves native work/queue; app restart recovers stored queue but requires reconciliation before uncertain continuation. Unsaved text remains current app-lifetime behavior.

## Integration and release gates

`7a3c7f7` collisions: TaskWorkSessions.tsx + tests (copy/layout/keyboard and completed note path); TaskDetail.tsx + tests (retention/guards); task_execution_service.rs (transactional final report and completed guards); task_service.rs (completion/hold guards). Additive migration/types/service contracts must preserve old rows and current terminal transaction. `9940d91` collision is TaskDetail's initialTab/load dependency and Compass focus/navigation, not provider execution; combine both and keep shared detail component.

Release gate: queue disabled and untouched effort must pass the exact existing baseline behavior/test suite; no existing working action may disappear or silently change. Then run focused new unit/native fake-provider race tests, existing public API/legacy data roundtrips and targeted UI/native-boundary E2E only where cheaper tests leave concrete gaps. No full E2E by default. Baseline known limitations should be recorded separately, not hidden or attributed to this design.

User-visible intentional changes needing approval: remove title editing; active Enter/enqueue mapping versus existing Enter/Run and IME/Shift+Enter; queued instructions authorize sequential automatic follow-ups; Stop alone pauses auto-follow-up; completion with pending queue requires cancel/resolve; model/effort invalidation prompts. Compatibility expectation is approval of these precise changes, never blanket removal of unrelated features. Preserve an explicit no-queue manual path throughout rollout.
